AgenticNetOS Desktop Lite

AgenticNetOS is a runtime for observable workflows and persona agents. Create one named specialist or a whole team, let them collaborate through shared context and explicit hand-offs, and improve the process from its complete history.

1. What this is

Use a workflow when the steps are known; give judgment-heavy work to a persona agent. You can create a developer who owns code changes, a health coach who remembers goals and boundaries, a domain expert who knows one business area, or several specialists who plan, build, review, and decide together. A team does not become a hidden group chat: every persona has a clear role and charter, exchanges visible work through the net, and can be inspected or stopped.

Underneath, every workflow, persona, and team is built from Agentic-Nets. A net gives an autonomous process what an ordinary chat lacks: memory that outlives the session, work that waits safely, typed context it can navigate, deterministic tools, schedules, hand-offs, audit history, and durable results. Start with a familiar persona or outcome; the net remains inspectable when you want to understand or change the machinery.

The Safe Product Team is one detailed product-delivery example, not a domain boundary. The same runtime models healthcare, research, operations, finance, support, logistics, and other domains as named personas, typed state, deterministic control, and historically analyzable processes.

Personas are the easiest place to begin, not the limit of the product. A net can represent a workflow, reusable context, domain memory, tool, team, human-interaction surface, goal system, or self-improving process. Studio application views such as Protocol, Interview, and Goals are themselves backed by ordinary installable nets rather than separate hidden databases.

The difference is not merely that AgenticNetOS can run agents. Every token movement, transition fire, tool result, approval, and structural change leaves an event-sourced history. The Protocol turns the important milestones into a readable team narrative, while the event trail remains the complete evidence underneath it. You can reconstruct a story, find where it waited, compare persona outcomes, and promote repeated successful work into deterministic tools.

Desktop Lite installs that runtime as one local app and connects it to Claude Code, Codex, or another MCP client. No server LLM or API key is required. Your connected client can be the brain, or a persona can use an installed Claude Code/Codex CLI for unattended work. If you later configure a server provider, ordinary agent and llm lanes run there instead.

New to Petri nets? You do not need them to start. Ask your client for what you want in plain language: “create a developer persona” is enough to begin. Section 3 explains the vocabulary when you are curious about what was built.

2. Start here (about five minutes)

  1. Install the package and launch AgenticNetOS. The tray icon appears and the local services start. The icon goes solid once everything is healthy.
  2. In the tray, choose Connect Claude Code (copy command) and paste the command into a terminal. For Codex, choose Connect Codex (copy config) and merge the block into ~/.codex/config.toml. Any other Streamable HTTP client: Copy MCP URL + Token.
  3. Start a new client session. MCP servers are attached at startup, so an already-running session will not see it.
  4. Ask for a status check.
Say this

Run readiness and tell me what I can do.

readiness walks the whole chain in one call: authentication, data engine, model, LLM provider, executor coverage. It answers with a verdict per layer plus a list of problems. If it comes back clean you are ready. If not, it names the layer that is unhappy instead of making you guess.

Choose the smallest starter pattern that matches the goal. For a complete product-delivery example, the Safe Product Team MCP playbook deploys a deterministic backlog/review backbone, repository context, bounded specialists, an approval gate, and Protocol reporting. It makes the execution choice visible instead of quietly assuming that a server model exists:

Say this

Use the start-safe-product-team playbook for this repository and product goal. Check readiness, show me the Product Manager, Architect, Developer, Reviewer, Release Guardian, and Chronicle charters and hand-offs, and tell me which backend will run them before building. Keep push and deploy approval-gated, report milestones to Protocol, and smoke-test one harmless story before arming the team.

If you need only one colleague, ask for a developer, research analyst, study mentor, operations specialist, or another role meaningful to you. Either way, give it one real task. Its output and history remain after the chat closes; tomorrow a new client can read Protocol, inspect the evidence, recall context, and continue without recreating the agent.

3. Seven ideas, sixty seconds

IdeaWhat it is
PersonaA named outcome owner with a charter, boundaries, context, inbox, and results. One persona or a team is the human-facing product.
PlaceA named container holding JSON documents. Think of a folder that is persistent, queryable and keeps its history.
TokenOne JSON document inside a place: a note, a task, an API response, a result.
TransitionSomething that acts. It reads tokens from places, does work, and writes tokens to other places.
NetPlaces and transitions wired together: a persona, team, context, tool, or automation you can inspect and change.
Application viewA human-friendly page over a net's semantic store roles. The page is a renderer; the event-sourced net remains the source of truth.
ModelA domain workspace holding nets. It is also the pause, budget, ownership, and cleanup boundary.

There are seven kinds of transition, but only three distinctions matter on day one:

  • Deterministic (pass, map, http, command): follow a fixed operation and do not call a model unless the command explicitly launches one. These are the backbone.
  • Thinking (llm, agent): use a server provider, a connected client, or a headless Claude Code/Codex session. agent is a bounded multi-step persona; llm is one inference.
  • Link: pure structure. It connects context with a typed relationship and never fires.

The useful instinct to build early: put deterministic transitions everywhere you can, and spend thinking only where judgment is genuinely required. That is what keeps this cheap.

4. What to build

4.1 One specialist with a real charter

spawn_persona creates the minimum complete agent: charter, task inbox, bounded agent transition, and output. Add a journal for observations, feedback for ratings, and config places for preferences that change. A charter should state outcomes, boundaries, allowed tools, when to ask a human, and what “done” looks like.

PersonaUseful charterImportant boundary
DeveloperOwn a repository change; inspect, implement, verify, report risksSmall scoped changes; no version-control or deployment action unless asked
Health coachRemember goals and constraints; reflect on check-ins; suggest small next actionsNo diagnosis or replacement for a clinician; journal is context, not a medical record
Domain expertAnswer and curate knowledge for one technical or business domainSeparate verified facts from inference; retain source and provenance

Presets provide developer, reviewer, researcher, operator, and assistant starting points. They are archetypes, not the product limit: describe any role in plain language. Use safe reasoning-only capability by default and grant execution only when the charter genuinely needs commands or tools.

4.2 A complete specialist team

A team is not one super-agent with every permission. It is a visible playbook: a concierge or triage role clarifies work, a specialist acts, a reviewer returns approved/needs-work/blocked, and a human-review place pauses anything consequential. The roles exchange tokens through shared places, so every hand-off is durable and inspectable.

One complete worked example is the Safe Product Team: Product Manager as the only user inbox; Architect for design and risk; Developer for scoped changes; Reviewer/QA for independent evidence; Release Guardian for the commit/push/deploy boundary; and Chronicle for readable reports. A Domain Expert, Operations watcher, or Security reviewer is added only when the product needs it. Small roles, bounded authority, explicit review, and no hidden chat state are the safety mechanism.

The built-in dev-team template is its zero-LLM deterministic backbone. Invoke the start-safe-product-team MCP prompt to add resident personas and an execution backend. On a full/server installation, Agent Hub's safe-product-team is the versioned six-persona package: it installs stopped, has typed product/repository and approval schemas, and grants no command/repository/release authority by default. Configure, verify, then arm its start plan. A forum or issue tracker is an optional adapter; the team's source of truth and reporting remain inside the model.

Repository access belongs in a shared registry, not in a persona's imagination. Store one config token per repository with its URL or executor-visible working directory, default branch, allowed write scope, build/test commands, and explicit commit/push/deploy policy. Never put credentials in that token. A story names a repositoryId; it never asks an agent to guess a path.

Say this

Start a Safe Product Team for <product goal> in <repository>. Keep routing deterministic, give each role the least capability it needs, preserve one story ID through every hand-off, require approval before external side effects, and make every milestone visible in Protocol.

4.3 Observe first, then improve

Agentic-Nets keeps three complementary views of the same work:

  • Event trail: complete low-level history of token mutations, bindings, fires, emissions, tool results, and lifecycle changes. Filter it by transition or story ID.
  • Status board: structured current/aggregate facts such as story, persona, stage, duration, verdict, and evidence. Use it to find rework and waiting time.
  • Protocol: the human-readable operational narrative in the installed Protocol net's entries role (the built-in template preserves p-protocol). Personas record decisions, approvals, milestones, warnings, failures, and what happens next. Open it directly from the tray or read it with protocol_tail.

Protocol is not a replacement for audit history; it is the explanation over the evidence. Ask questions such as “where did STORY-42 wait?”, “which persona causes most rework?”, “what context version improved approvals?”, or “which repeated step is ready to crystallize?” Then use event_trail, net_stats, usage_report, and the stored feedback to answer rather than guessing.

Say this

Read Protocol and the event trail for this story. Reconstruct every hand-off, show wait time, rework, tool/test evidence and final approval, then propose one safe persona/context/process improvement. Do not change anything until you show the evidence.

4.4 Net-backed application views

A full page in Studio does not need a new backend subsystem. AgenticNetOS can install an ordinary NetHub session whose manifest names semantic store roles, declared append actions, and a renderer. MCP calls application_list and application_describe, so a persona discovers where to write instead of memorizing place IDs.

  • Protocol maps an entries role to a readable timeline over the evidence.
  • Interview maps prompts → responses → decisions. A developer, architect, coach, or domain expert can offer choices and free-text input, end its current fire, and resume when the response token arrives.
  • Goals maps goals → progress → outcomes. The user owns the desired outcome; autonomous processes append progress evidence against it.
Say this

List the installed application nets. If Interview and Goals are present, read my active goals, then use Interview whenever you need a plan choice or missing requirement. Report meaningful milestones to Protocol. Resolve semantic roles from each manifest; do not guess place IDs.

Interview responses are context, not automatic authorization for a risky external effect. Push, deploy, payment, deletion, or publication still needs the team's explicit approval policy. These templates are examples: the same contract can back a clinical intake, incident room, compliance review, research notebook, or another domain-specific view.

4.5 Domain agents and context playbooks

Plain recall is flat; real domains have relationships. Put knowledge, decisions, constraints, examples, incidents, and insights into places or reusable context nets. Attach the same billing context to a domain expert, developer, and reviewer instead of copying one enormous prompt into all three.

memory_link and link transitions add typed relationships such as contains, references, derives-from, and supersedes. A link never fires or moves a token; it lets an agent walk only the relevant neighborhood with memory_graph. Use domain_memory_write when a fact belongs to the model's domain and should be shared by every attached persona.

Say this

Create a billing domain expert plus a billing context net for glossary, rules, examples, incidents, decisions, and insights. Attach it with typed links and show what other personas could safely reuse.

4.6 Local hands, schedules, and headless CLI agents

Schedules make non-link transitions act while nobody is chatting. Deterministic map, pass, http, and command lanes are the cheap, reliable backbone: collect data, run a build, make a backup, probe a URL, or route a verdict. The watcher template is a zero-LLM sentinel that probes and alerts on a cron.

When a persona needs judgment and there is no server provider, there are two unattended CLI patterns. Prefer an agent lane with llmMode:"bash" and binary:"claude" or "codex" for a bounded, tool-using persona. It keeps the agent loop, capabilities, context, and audit. Use a command lane for a one-shot job whose contract is simply stdin to stdout:

printf '%s' '<task>' | claude -p --allowedTools 'Read,Grep' --no-session-persistence
printf '%s' '<task>' | codex exec --ephemeral --sandbox read-only -

Pipe prompts through stdin; never hide dynamic user text inside nested shell quotes. Keep tools, sandbox, working directory, and schedule least-privilege. The CLI must be installed and reachable by the Desktop master/executor process. A scheduled local runtime still requires the machine to be awake and AgenticNetOS running.

READY means the executor is polling this model. STANDBY means it is available and will activate after the first command assignment. Only UNAVAILABLE blocks command lanes.

4.7 A net that learns without rewriting itself in secret

Agentic-Nets can become more capable over time while keeping changes reviewable. Work writes outcomes to a journal; feedback links success or failure to the task and context version; a context-curator proposes concise knowledge updates; a reviewer or human approves them. Typed derives-from and supersedes links preserve history and make rollback possible.

When the same reasoning succeeds repeatedly, crystallize_session captures what was done and scaffold_tool_net turns it into a reusable deterministic tool. Novel work stays with personas; learned procedures become cheaper, faster, and safer transitions. Self-learning means evidence and reviewed promotion, never silently loosening the charter or safety boundary.

4.8 Templates and the rest of the platform

There are three reuse layers. MCP prompts/playbooks guide a connected model through environment-aware setup. Built-in starter templates deploy common deterministic topologies. NetHub/Agent Hub packages are versioned portable artifacts: publish or install a net, whole session/model, persona team (agent), context system, tool-net, tool, catalog, or blob. Agent/context packages land stopped so configuration and safety policy can be checked before execution.

Agent Hub also ships Model Steward, a domain-neutral advisory meta-agent. It reviews the current model's sessions, nets, token flow, transition health, executors, and event evidence; reports bottlenecks, safety risks, strengths, and crystallization candidates; and can write only its own findings. It cannot change or operate the nets it reviews.

  • Event sourcing: tokens and fires retain provenance; Protocol and event_trail explain the readable narrative and underlying evidence.
  • Concurrency and backpressure: specialists work in parallel; capacities stop a fast producer from overwhelming a reviewer.
  • Time: six-field cron and intervals arm teams, watchers, and maintenance; scheduler_status explains silent lanes.
  • Control: stop one lane or pause_model as a whole-domain kill switch; resume restores exactly what was paused.
  • Sharing: publish and install nets, tools, contexts, agent sessions, or models through NetHub/Agent Hub with credentials scrubbed.
  • Visual editing: Studio shows the same places, transitions, links, schedules, tokens, and protocol that MCP and CLI operate.

6. What runs while you are away

Always ask two questions: where does this persona think? and does that place still exist when my chat disconnects? Desktop Lite has several correct answers.

No server provider does not mean no unattended agents. Provider-backed llm/agent lanes wait for a connected client, but a CLI-backed agent (llmMode:"bash") runs on master, and a command lane can run a one-shot headless Claude Code/Codex job on the executor. Both require the chosen CLI to be installed and reachable. Deterministic lanes are unaffected.

The built-in headless-cli-reviewer is the reference for the one-shot command path: a map creates a canonical CommandToken, the executor invokes read-only Claude Code or Codex, and the complete result remains in a durable place. Use a CLI-backed agent instead when the work needs a resident persona, tool loop, memory, and capabilities.

LaneClient connectedClient disconnected
Scheduled map, pass, http, commandRunsRuns, on schedule
Provider-backed llm/agent, provider disabledConnected client can serve itWaits safely
agent with llmMode:"bash", CLI reachableRuns on masterRuns, including schedules
command piping to a headless CLIRuns on executorRuns, including schedules
llm/agent with a server provider configuredRuns on masterRuns, including schedules
Lane marked externalConnected client serves itWaits safely

Nothing is lost by being offline. The tokens sit in their input places and the work is simply pending. That is the whole reason work is stored as tokens rather than held in a conversation: an interrupted pipeline is paused, not failed.

spawn_persona execution:"auto" chooses the server when its provider is ready and an honest connected-client lane otherwise. It does not guess that master can see a CLI merely because your chat client can. A Claude Code or Codex client on the same machine should propose its matching explicit backend; select it only when the Desktop process can reach that binary.

6.1 Your assistant should tell you about the backlog

When a client connects, the MCP server tells it how many provider-backed lanes are waiting, so a well-behaved client reports something like "3 AI lanes have work waiting for me, shall I run them?" and works through them on your say-so. It sees every AI lane you have, not just ones you flagged, so a lane you forgot about still gets found.

If your client stays quiet about it, ask directly. Either of these does the job:

Say this

Check readiness. Are any AI lanes waiting for you? If so, run them.

Or invoke the prompt your client exposes as work-external-fires.

6.2 Three ways to run reasoning unattended

  1. CLI-backed persona: keep the complete agent loop with llmMode:"bash" and Claude Code/Codex on the Desktop host.
  2. Headless command job: pipe a bounded prompt to the CLI on the executor; best when stdin-to-stdout is the whole contract.
  3. Server provider: configure Ollama or Anthropic in LLM Settings; ordinary agent/llm lanes and their schedules are then master-owned.
A middle option, if you are comfortable at a terminal. The agenticos CLI can serve these lanes too, using its own model: agenticos transition lanes --all to see them and agenticos transition serve to run them. Useful for a scheduled script that drains the backlog without opening a chat client. It is a separate install (it does not ship inside this app), so treat it as an extra rather than the normal path.

Connected-client reasoning uses that client's account. Headless CLI lanes use the installed CLI's account. Server lanes use the configured provider. usage_report measures provider calls and estimates bash-mode agent usage; a command that launches its own model is outside that meter, so include that cost in the persona's journal if it matters.

One hard requirement either way: the machine has to be awake with the app running. Desktop Lite is a local runtime, not a cloud service. Turn on Start at Login if you want it always there.

8. Studio, the visual side

Studio is optional. You can run everything through your MCP client and never open it. But seeing your first net drawn as a graph is usually the moment the model clicks, so it is worth a look early.

Inside you can inspect places and their tokens, follow the arcs, and use application views over the same state. Protocol has its own model selector, independent of the editor, so you can inspect one model or merge all of them without disturbing what you are editing. It supports search, level filtering and grouping by source, day, tag or model.

Interview and Goals are the same architectural pattern: the tray opens a purpose-built renderer, while MCP and nets interact through manifest-declared roles and actions. Uninstall the view and the net state remains standard Agentic-Net state; export the session and the contract travels with it.

A good team writes only meaningful milestones to Protocol—story accepted, design chosen, change ready, review rejected or approved, release authorized, deploy verified—while the event store keeps every mechanical detail. Click from the readable report into tokens and transition history when a claim needs proof. This combination is the central Agentic-Nets advantage: operational visibility without forcing a newcomer to read raw logs.

For a persona or team, Studio makes the charter, inboxes, specialist hand-offs, typed context links, review gates, and backpressure visible. The same design applies to the full/server edition; that edition mainly changes where services, providers, and executors run.

9. Cost and safety

  • No hidden server-model bill by default. It ships with no server-side LLM. Connected clients and headless Claude Code/Codex lanes use those products' own accounts.
  • Local only. Every listener binds to 127.0.0.1. There is deliberately no switch to expose it to the network; that belongs to the server deployment.
  • The MCP endpoint needs its token, generated per installation, which is why you copy it from the tray rather than from any documentation.
  • There is a kill switch. "Pause the model" stops every running transition, and resuming restores exactly the set that was paused.
  • Secrets stay out of your nets. Transition credentials live in an encrypted local vault, scoped per transition, never in the net definition you might export or share.

12. When to move beyond Lite

Desktop Lite is deliberately one machine, one user, one executor, loopback only. It is a creator and operator environment rather than a production deployment.

Move to the Docker deployment when you need remote access, several executors, clustering, the monitoring stack, or production lifecycle controls. Your work travels with you: publish a net with hub_publish and install it on the server with hub_install.

Reference documentation for this edition ships alongside the app as DESKTOP-LITE.md. The platform documentation is in Studio under Docs, and the MCP server answers search_knowledge offline.
