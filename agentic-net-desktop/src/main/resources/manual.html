AgenticNetOS Desktop Lite

Persistent memory, a clock, and a pair of hands for the AI assistant you already use.

1. What this is

You already have something that can think: Claude Code, Codex, Cursor, or another MCP client. What it does not have is a memory that outlives the session, a clock that fires while you sleep, and somewhere to put work so it can be picked up again tomorrow.

Desktop Lite is that missing half. It installs as one desktop app, runs entirely on your own machine, and offers itself to your MCP client as a set of tools. Your client stays the brain. Desktop Lite is the memory, the hands, and the clock.

There is no API key to enter and no cloud service involved. By default nothing here calls an LLM on its own: the reasoning happens in the client you already pay for.

New to Petri nets? You do not need them to start. Ask your client for what you want in plain language and it will build the net. Section 3 explains the vocabulary when you are curious about what it built.

2. Start here (about five minutes)

  1. Install the package and launch AgenticNetOS. The tray icon appears and the local services start. The icon goes solid once everything is healthy.
  2. In the tray, choose Connect Claude Code (copy command) and paste the command into a terminal. For Codex, choose Connect Codex (copy config) and merge the block into ~/.codex/config.toml. Any other Streamable HTTP client: Copy MCP URL + Token.
  3. Start a new client session. MCP servers are attached at startup, so an already-running session will not see it.
  4. Ask for a status check.
Say this

Run readiness and tell me what I can do.

readiness walks the whole chain in one call: authentication, data engine, model, LLM provider, executor coverage. It answers with a verdict per layer plus a list of problems. If it comes back clean you are ready. If not, it names the layer that is unhappy instead of making you guess.

Now the first genuinely useful thing:

Say this

Deploy the working-memory template, then store this decision: we prefer TypeScript over Python for internal scripts, because the team already reviews TypeScript.

Tomorrow, in a brand new session that knows nothing about today, say "recall what we decided about scripting languages". That round trip is the whole product in miniature.

3. Five ideas, sixty seconds

IdeaWhat it is
PlaceA named container holding JSON documents. Think of a folder that is persistent, queryable and keeps its history.
TokenOne JSON document inside a place: a note, a task, an API response, a result.
TransitionSomething that acts. It reads tokens from places, does work, and writes tokens to other places.
NetPlaces and transitions wired together. A workflow you can look at, inspect and change.
ModelA workspace that holds nets. A fresh install has one called default.

There are seven kinds of transition, but only three distinctions matter on day one:

  • Deterministic (pass, map, http, command): run locally, no AI involved, no cost. These are the backbone.
  • Thinking (llm, agent): need a language model. In Desktop Lite your connected client supplies it.
  • Link: pure structure. It connects places into a graph and never fires.

The useful instinct to build early: put deterministic transitions everywhere you can, and spend thinking only where judgment is genuinely required. That is what keeps this cheap.

4. What to build

4.1 A memory that survives the session

This is the one to start with. Every new client session begins from zero, so you re-explain the project, the conventions, the decisions and the pitfalls that bit you last month. Desktop Lite ends that.

Write with memory_write (into inbox, notes, decisions or knowledge), read with memory_recall. The working-memory template sets up those places along with a distiller that keeps raw capture tidy.

It is shared, not per-client: what Claude Code wrote this morning, Codex reads this afternoon.

4.2 Context you can compose, not just recall

Plain recall is flat, and real work is not. A project has conventions, which relate to pitfalls, which came out of a particular incident, which is why a certain rule exists. Dumping all of that into one blob is how you burn a context window and still miss the relevant part.

Nets model the structure directly. Give each context its own place or its own small net. Connect the ones that genuinely relate with memory_link, or with link transitions when the connection should be part of the net itself. Then memory_graph lets your assistant walk the neighborhood instead of swallowing everything.

The payoff is that context becomes navigable. Ask about billing and you get the billing glossary, plus the API conventions it links to, plus the two failure modes recorded against it. Not the other forty documents.

Say this

Create a context net for our billing domain, write these facts into it, and link it to the API conventions place.

Later: what do you know about billing? Follow the links before you answer.

A few habits that make this work well:

  • One net per context domain, so each stays independently editable and shareable.
  • Link only real relationships. A graph where everything connects to everything says nothing.
  • Use domain_memory_write when a fact belongs to the domain itself and every agent touching it should see it, rather than to your current session.

4.3 Turn a session you keep repeating into a net

If you do the same thing every Monday, that is not really a session. It is a workflow that has not been written down yet. Collect the week's repository activity and summarize it. Check the dependency advisories. Rank yesterday's errors. Pull a report and file the numbers somewhere.

Each of those becomes a net with a schedule. set_schedule accepts a six field cron expression and an explicit timezone such as Europe/Berlin, which matters more than it sounds: without it, twice a year your morning job quietly moves by an hour.

Say this

Build a net that fetches that URL every weekday at 07:00 Europe/Berlin, pulls out the headline items, and stores them in a place I can read later. Then tell me what you armed.

Deterministic schedules keep running with no client attached and at no cost. Monday morning you just ask what landed. If a step in the net needs judgment rather than a rule, that step is an AI lane and section 6 applies to it: worth knowing before you rely on a 07:00 summary being written at 07:00.

4.4 A persona that works while you do something else

spawn_persona stands up a complete self-driving worker in one call: a charter, a task inbox, an agent transition watching that inbox, and an output place. Presets cover the common archetypes (developer, reviewer, researcher, operator, assistant). Spawn several and they work in parallel.

The best uses are the ones where you want a different opinion rather than a second pair of hands. A reviewer that argues against your design before you commit to it. A researcher that keeps digging through a question while you get on with something else. Give two personas the same question and compare where they disagree; the disagreement is usually the interesting part.

Worth knowing up front. A persona is an agent lane, so it thinks, so it needs a model. With no LLM configured your connected client does that thinking, which means a persona advances while you are there and its tasks queue safely when you are not. Giving it a cron does not change that. Section 6 explains the rule and the two ways to change it.

4.5 A watcher that costs nothing

The watcher template is a sentinel with no AI in it at all: probe a URL on a cron, call a webhook when the answer is not 200. It runs on schedule whether or not anything is connected, and it never bills anybody.

It is also the clearest illustration of the point in section 3. Watching something does not require intelligence. Deciding what to do about it might.

4.6 The hands: local commands on a schedule

Command transitions run shell commands on your own machine through the bundled executor. Backups, syncs, a build, log tidying, the script you always mean to run and never do.

One thing that confuses newcomers: the executor reports a state per model. READY means it is polling because a command lane exists. STANDBY means it is available but no command lane has been assigned yet, which is completely normal on a fresh install. Only UNAVAILABLE is a real problem. Ask for list_executors if you want to see it.

4.7 Make the repeated thing cheaper over time

crystallize_session records what a session actually did, both into memory and as a replayable tool net. It supports the pattern this platform is built around: the first run needs full reasoning, and once the shape is known you replace the thinking with deterministic transitions.

Done consistently, your cost curve bends downward as your automation grows, which is the opposite of what usually happens.

6. What runs while you are away

This is the single most important thing to understand about Desktop Lite, and the one that surprises people. It follows directly from there being no server-side LLM by default.

With no LLM configured, your MCP client is the only thing that can run llm and agent transitions. Those lanes therefore cannot run on a schedule while you are away. You can put a cron on one, and it will be accepted and displayed as armed, but nobody dispatches it. It runs when a client connects and serves it. Deterministic lanes are completely unaffected.

Nothing about the lane changes because of this. It still deploys, still starts, still shows as running if you started it. There is simply no model on this machine for the server to run it with, so the server leaves it alone rather than failing it over and over. Your assistant picks it up instead.

LaneClient connectedClient disconnected
Scheduled map, pass, http, commandRunsRuns, on schedule
llm / agent, default Lite profileRuns, your client does the thinkingWaits, schedule or not
llm / agent with a provider configuredRunsRuns, on schedule

Nothing is lost by being offline. The tokens sit in their input places and the work is simply pending. That is the whole reason work is stored as tokens rather than held in a conversation: an interrupted pipeline is paused, not failed.

You do not have to mark or configure anything for this. Build a net the normal way and the AI lanes in it simply wait for something that can think. If you press fire on one by hand, you get a plain refusal saying there is no model configured, and your input token stays exactly where it was.

6.1 Your assistant should tell you about the backlog

You do not have to remember any of this. When a client connects, the MCP server tells it that this session is the runtime for those lanes and how many are waiting, so a well-behaved client reports something like "3 AI lanes have work waiting for me, shall I run them?" and works through them on your say-so. It sees every AI lane you have, not just ones you flagged, so a lane you forgot about still gets found.

If your client stays quiet about it, ask directly. Either of these does the job:

Say this

Check readiness. Are any AI lanes waiting for you? If so, run them.

Or invoke the prompt your client exposes as work-external-fires.

6.2 If you want them to run unattended

Configure a model in LLM Settings (tray, or Studio's settings): a local Ollama, or an Anthropic key. Master then owns those lanes and their schedules run like any other, with nobody connected.

A middle option, if you are comfortable at a terminal. The agenticos CLI can serve these lanes too, using its own model: agenticos transition lanes --all to see them and agenticos transition serve to run them. Useful for a scheduled script that drains the backlog without opening a chat client. It is a separate install (it does not ship inside this app), so treat it as an extra rather than the normal path.

That is the real trade. Leave it disabled and your assistant does the thinking, which costs you nothing extra and keeps everything local, but AI lanes only advance while you are there. Configure a provider and they run overnight, billed to that provider. Deterministic and command lanes need neither choice; they always run.

One hard requirement either way: the machine has to be awake with the app running. Desktop Lite is a local runtime, not a cloud service. Turn on Start at Login if you want it always there.

8. Studio, the visual side

Studio is optional. You can run everything through your MCP client and never open it. But seeing your first net drawn as a graph is usually the moment the model clicks, so it is worth a look early.

Inside you can inspect places and their tokens, follow the arcs, and watch fires arrive in the Protocol view. Protocol has its own model selector, independent of the editor, so you can inspect one model or merge all of them without disturbing what you are editing. It supports search, level filtering and grouping by source, day, tag or model.

9. Cost and safety

  • No surprise bills from Desktop Lite. It ships with no server side LLM. Your client's usage is billed by your client, the way it already was.
  • Local only. Every listener binds to 127.0.0.1. There is deliberately no switch to expose it to the network; that belongs to the server deployment.
  • The MCP endpoint needs its token, generated per installation, which is why you copy it from the tray rather than from any documentation.
  • There is a kill switch. "Pause the model" stops every running transition, and resuming restores exactly the set that was paused.
  • Secrets stay out of your nets. Transition credentials live in an encrypted local vault, scoped per transition, never in the net definition you might export or share.

SymptomAsk your client for
Nothing works at allreadiness, which names the unhappy layer
An AI lane never ran overnightExpected without a configured provider, not a fault: see section 6. scheduler_status marks these lanes willNotFireUnattended
Firing an AI lane by hand refusedSame cause, and deliberate: with no model configured the server says so instead of failing repeatedly. Your input token is untouched, so serving it later works
A scheduled net went silentscheduler_status: it reports stopped and invalid schedules, and keeps armed, fired and succeeded times apart
A command lane is queued with no outputlist_executors, or executor coverage in net_stats

Spending more than expectedusage_report, ranked per transition

A schedule that cannot be understood does not run. If a cron expression or timezone is malformed the lane fires never rather than every poll, and scheduler_status tells you why. Silence there is a reason to look, not a reason to wait.

12. When to move beyond Lite

Desktop Lite is deliberately one machine, one user, one executor, loopback only. It is a creator and operator environment rather than a production deployment.

Move to the Docker deployment when you need remote access, several executors, clustering, the monitoring stack, or production lifecycle controls. Your work travels with you: publish a net with hub_publish and install it on the server with hub_install.

Reference documentation for this edition ships alongside the app as DESKTOP-LITE.md. The platform documentation is in Studio under Docs, and the MCP server answers search_knowledge offline.
